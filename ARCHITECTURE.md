# ARCHITECTURE Design Document

## 1. Обзор архитектуры (High-Level Overview)

Проект спроектирован по принципам Clean / Hexagonal Architecture.
Цель — изолировать бизнес-ядро (Core Domain) от внешних интерфейсов и инфраструктуры.

**Ключевые концепции:**
*   **Ports & Adapters:**
    *   **Primary Adapters (Вход):** Контроллеры (`*.controller.ts`) и шлюзы для входящих событий (например, вебхуки). Они транслируют внешние запросы в вызовы доменных сервисов (Use Cases). Пример: `Webhook Gateway` использует **Adapter Pattern** для маппинга JSON-пейлоада от внешнего магазина во внутреннюю команду `CreateOrderCommand`.
    *   **Secondary Adapters (Выход):** Репозитории (`*.repository.ts`) и клиенты очередей (`*.queue.service.ts`). Они реализуют интерфейсы, определенные в доменном слое, для взаимодействия с базой данных, очередями и другими внешними системами.
*   **Dependency Inversion:** Инфраструктурные детали (Prisma, BullMQ) зависят от абстракций доменного слоя, а не наоборот.

## 2. Архитектурные решения

### 2.1. Сначала тесты (TDD)
Мы договорились: сначала пишем тесты, а потом уже код. Это железное правило!
**Что проверяем:**
*   **Счастливый путь:** Основные сценарии использования, когда всё работает как надо.
*   **Ограничения и валидация:** Проверка бизнес-правил (например, чтобы не продать то, чего нет на складе, или не вернуть больше, чем купили).
*   **Идемпотентность:** Гарантия того, что повторные запросы (создание заказа, вебхук) не приводят к дублированию данных или некорректному состоянию.

### 2.2. Multi-tenancy и Контекст запроса
*   **Подход:** Row-Level Multi-tenancy. `tenantId` (UUID) присутствует во всех ключевых таблицах данных. Для производительности запросов обязателен индекс `@@index([tenantId])`.
*   **Контекст запроса:** Для сквозной передачи `tenantId` и `traceId` используется `AsyncLocalStorage` (CLS). Контекст инициализируется в `Auth Middleware` и доступен во всех синхронных вызовах внутри одного запроса.

### 2.3. Асинхронные операции (Workers)
*   **Изоляция:** Воркеры `BullMQ` запускаются в отдельных процессах, но переиспользуют доменные сервисы. Это обеспечивает разделение ресурсов между API и фоновыми задачами.
*   **Передача контекста:** `AsyncLocalStorage` не работает "из коробки" при передаче задач в очередь. Поэтому **контекст (`tenantId`, `traceId`) явно сериализуется в payload задачи**. Воркер, принимая задачу, восстанавливает CLS-контекст перед выполнением доменной логики. Это гарантирует, что мульти-тенантность и трассировка работают и в фоновых задачах.

### 2.4. Работа с данными (PostgreSQL 18 + Prisma)
 * **ORM:** Prisma используется исключительно в слое адаптеров (`adapters/prisma`) для инкапсуляции логики доступа к данным.
 * **Типы данных:** Предпочтение отдается нативным типам PostgreSQL (`@db.Uuid`, `VARCHAR`) для строгой типизации и производительности.

### 2.5. Управление конкурентностью (Concurrency Control)
Проблема Race Conditions решается без блокирующих очередей на критическом пути (создание заказа), чтобы обеспечить быстрый ответ API.
 * **Остатки (Stock): Optimistic Concurrency Control**
   * В таблицу `StockLevel` добавляется поле `version` (число).
   * Перед обновлением остатка сервис читает текущую версию.
   * `UPDATE` выполняется с условием `WHERE version = :read_version`. Если запись была изменена другим процессом, `UPDATE` не затронет ни одной строки, и сервис может повторить операцию или вернуть ошибку.
   * Дополнительно используются атомарные операции `UPDATE stock SET available = available - :qty WHERE ...`.
 * **Аудит (Audit Log): Pessimistic Locking**
   * Для гарантии строгой целостности цепочки хешей (`Hash Chain`) применяется блокировка на уровне БД.
   * Внутри транзакции последняя запись аудита для данного тенанта блокируется через `SELECT ... FOR UPDATE`. Это предотвращает параллельную вставку и гарантирует, что `prevHash` будет корректным.
 * **Идемпотентность (Webhooks):**
   * Для защиты от дублирующихся вебхуков используется уникальный индекс в таблице `webhook_events` по полям `(tenantId, eventId)`.

### 2.6. Mapper Pattern в Репозиториях
*   **Проблема:** Дублирование кода маппинга между структурами БД (Prisma) и Доменными сущностями.
*   **Решение:** В каждом репозитории должны быть реализованы приватные методы:
    *   `toDomain(persistenceEntity): DomainEntity` — преобразование из БД в домен.
    *   `toPersistence(domainEntity): PersistenceEntity` — (опционально) преобразование из домена в формат для сохранения.
*   **Использование:** Методы `find*` и `create` должны использовать эти мапперы, а не дублировать логику трансформации (особенно `any` касты и маппинг вложенных отношений).

## 3. Стек технологий
 * **Runtime:** Node.js 20+ (LTS)
 * **Framework:** NestJS
 * **Database:** PostgreSQL 18
 * **ORM:** Prisma
 * **Queue:** Redis + BullMQ
 * **Documentation:** Swagger (OpenAPI) Code-First
 * **Testing:** Jest

## 4. Ограничения
 * **Валюта:** Система оперирует только количественным учетом (qty), финансовые операции не входят в скоуп.
 * **Масштабирование аудита:** Реализация Audit Log через пессимистическую блокировку в PostgreSQL подходит для средних нагрузок (SMB). Для высоконагруженных систем (Enterprise) потребуется переход на специализированные Append-Only Log системы (например, Kafka или NATS), что выходит за рамки текущего проекта.
